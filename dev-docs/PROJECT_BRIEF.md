# MedCite 项目立项文档

更新时间：2026-10-27
版本：1.0
项目阶段：多类型来源检索和医学期刊 NLM 引用已部署，并完成基本线上验收

## 一、项目概述

MedCite 是一个帮助学生快速生成规范参考文献的网站。首版从一个范围清楚、容易验证的场景开始：医学生输入英文医学期刊文章的 DOI，得到可检查、可编辑、可复制的 NLM 格式参考文献。

项目负责人是编程初学者，因此首版优先控制功能数量和技术复杂度，先完成一条快速、可靠的完整流程，再依据实际使用情况扩展。

## 二、目标用户与需求

### 首批目标用户

需要用英文医学期刊文章完成课程论文或小型作业的医学生。这是首批切入人群假设，不代表产品以后只服务医学生。

### 用户要完成的事

用户手上有一篇医学论文的 DOI，希望不用自己查找并逐项整理书目信息，就能快速得到符合指定规范的参考文献，并在复制前检查和修正信息。

### 产品价值假设

- 操作简单，尽量减少查找和填写步骤。
- 生成速度快，让用户尽快拿到可复制结果。
- 信息不完整时清楚提醒，允许用户自己检查和编辑。

“简单”是产品定位假设，尚未通过真实用户研究验证；不得描述为已证实的独特优势。

## 三、首版产品范围

### 支持的输入和资料

- 接受纯 DOI 或 DOI 链接，直接查询对应记录。
- 接受文章标题或关键词，并展示最多 5 条期刊文章候选供用户选择。
- 接受公开网页 URL 和 ISBN，查询并展示可取得的来源资料。
- 当前只有英文医学期刊文章可生成 NLM 引用；网页和图书目前只提供来源资料，不生成引用格式。
- 预印本、数据集或其他不受支持的类型不套用期刊文章格式，并提供说明。

### 引用格式

- 首版以 NLM《Citing Medicine》为参考文献格式基准。
- 产品明确标注 NLM，不承诺满足每一本医学期刊额外的投稿格式要求。
- 如果自动格式规则与 NLM 官方样例或选定规范不一致，应以查证结果为准并修正实现。

### 用户流程

1. 用户输入 DOI、DOI 链接、标题/关键词、公开网页 URL 或 ISBN，并可选择输入类型或使用自动识别。
2. 点击“生成引用”；标题/关键词搜索时，先从候选列表选择来源。
3. 网站查询来源资料，并判断当前是否支持该来源的引用格式。
4. 英文医学期刊文章可显示 NLM 引用；网页和图书显示来源资料，并说明对应格式暂未支持。
5. 用户可复制可用的引用，或展开信息编辑；编辑后引用预览同步更新。
6. 查不到、查询失败、类型不支持或关键字段缺失时，页面给出清楚的提示和可行的下一步。

### 需要展示和允许编辑的信息

- 文章标题
- 作者
- 期刊名称
- 出版年份
- 查询到时显示卷号、期号和页码

作者、标题、期刊名称或年份为空时提醒用户。卷号、期号或页码为空时不一定意味着错误，部分文章没有传统的卷期页信息。

系统只提醒关键字段是否为空，不声称已核实字段内容的真实性或准确性。书目信息可能来自外部元数据来源，用户应能检查并编辑。

### 首版验收方向

- 用户能通过 DOI、标题/关键词、URL 和 ISBN 查找来源；标题/关键词可选候选来源。
- 英文医学期刊文章可从 DOI 或标题候选生成 NLM 引用并复制。
- 网页和图书查询成功时明确说明引用格式尚未支持，不显示伪造的引用。
- 常见且受支持的 DOI 能生成可复制的 NLM 参考文献。
- 用户编辑论文信息后，引用预览随之更新。
- 查不到记录、查询失败、类型不支持和关键信息缺失时，都有明确反馈。
- 速度是首版重点。正常网络下常见 DOI 约 5 秒内显示结果是暂定目标，必须以实际测量验证；查询较慢时显示清楚的等待状态。

## 四、明确暂不纳入首版的功能

- 批量输入 DOI
- 账号、个人资料和项目管理
- 多人协作与分享书目
- 浏览器插件
- Google Docs 深度集成
- Zotero 或 Mendeley 同步
- 大量引用格式
- 图书、网页、视频、报纸等其他来源的引用格式

这些功能留待核心流程可用后再评估，不应提前加入首版。

## 五、后续发展方向（候选规划，尚未承诺）

扩展前先验证首版是否真的让目标用户更省时，并收集他们在实际作业中的困难。候选方向如下，顺序可依据反馈调整：

1. **整理多条参考文献**：批量添加 DOI、在一个书目或项目中保存和排序条目。
2. **账号与协作**：跨设备保存项目、分享书目、邀请同学共同整理。此阶段才评估登录、权限和数据库。
3. **更多格式与导出**：增加常用引用格式、BibTeX/RIS，以及 Word 或 Google Docs 相关导出能力。
4. **浏览器插件**：在浏览论文页面时快速取得书目信息，并调用网站已有的查询和格式处理能力。
5. **更多资料类型**：根据目标用户反馈，再评估网页、图书、视频等来源。

以上是待验证的产品方向，不代表已经排期或纳入首版。

## 六、已选技术栈与前端组织

### 首版选择

- **网站框架：Next.js（App Router）**。页面和小型服务端接口放在同一个项目中，适合首版单页流程，也为后续插件调用查询接口留出路径。
- **编程语言：TypeScript**。在 JavaScript 基础上增加类型检查；可帮助发现论文信息字段不匹配等问题，但初学时需要多学一些语法规则。
- **UI 组件库：Mantine**。首版使用常见基础组件，如按钮、输入框、提示框和加载状态；页面整体布局与品牌外观由 MedCite 自己设计。
- **页面样式：CSS Modules**。仍使用普通 CSS 语法，但样式按组件隔离，减少不同区域的样式互相影响；与 Mantine 配合使用。
- **服务端接口：Next.js Route Handlers**。DOI 查询和来源适配放在服务端接口中，避免把外部数据源细节散落在页面代码里。
- **数据库与账号：首版不使用**。当前主流程不需要保存用户项目；等项目管理成为已确认需求后再选择数据库和认证方式。

### 当前实现进度（2026-10-27）

- 已建立 Next.js App Router + TypeScript 项目基础，并采用 Mantine 与 CSS Modules。
- 已搭建英文浅色首页、品牌头部、多类型来源搜索区域和引用结果预览，适配窄屏布局。
- 已接入 `POST /api/citations/lookup`：DOI 查询 PubMed/Crossref，标题/关键词通过 Crossref 提供期刊文章候选，URL 和 ISBN 查询可用来源资料。
- 标题搜索使用 Crossref 标题检索并过滤非期刊文章记录；外部来源请求超时设为 10 秒。
- 首页 HTML 使用 `Cache-Control: no-store`，避免部署后缓存的旧 HTML 引用已替换的 JavaScript 文件。
- 英文医学期刊文章生成 NLM 引用；网页和图书目前只展示来源资料，尚无对应引用格式。
- 页面已接入查询中的等待状态、成功结果、缺失字段提醒、错误提示、编辑和复制流程。
- 依赖已安装；`npm run typecheck`、`node --test` 与 `npm run build:vinext` 均通过；线上主要输入流程已验收。
- 已在线验证 DOI 与来源搜索流程；NLM 格式仍需用官方样例逐条复核，约 5 秒暂定速度目标也需独立性能测试；详见 `IMPLEMENTATION_SOURCE_OF_TRUTH.md`。

### 前端结构与模块边界

- 页面路由和整体布局放在 Next.js 的 `app` 目录。
- DOI 输入、引用结果和论文信息编辑属于引用功能，集中放在 `features/citation`，避免查询流程与页面布局混在一起。
- 多处复用的通用组件放在 `components`；只在确实复用或有清楚职责时才抽成组件，不把每个小元素都拆开。
- 之后接入元数据查询和引用格式生成时，将它们与页面展示分开，便于替换数据来源或调整格式规则。首版页面骨架阶段不提前实现这些逻辑。

### 视觉、多语言与主题

- 首版使用英文界面和浅色主题，不做语言切换或暗色模式开关。
- 将界面文案集中管理，降低以后增加中文等语言时的修改成本；首版不引入完整的国际化框架。
- 使用少量 CSS 变量统一颜色、字号、间距和圆角。白底、深蓝文字、醒目的暖色主按钮是当前视觉方向，具体色值待页面设计时确认。

### 选择理由

- 首版是一个输入 DOI、展示结果、编辑和复制的轻量网站，不需要先搭建完整后台。
- DOI 查询涉及外部数据源；网页和服务端接口在同一项目内，便于入门阶段理解和维护。
- Mantine 与 Next.js 有官方接入说明，并支持 CSS Modules；基础控件可以直接复用，页面仍可按 MedCite 的定位定制。
- 以后浏览器插件可以复用服务端查询接口；后续增加账号和项目功能时，再逐步增加持久化能力。
- 先不增加数据库、登录、完整多语言系统和大量第三方服务，能把精力集中在核心引用流程和格式准确性上。

### 后端框架方案（已讨论，待实现验收）

- **服务端入口：**使用 Next.js Route Handler 提供 DOI 查询接口，暂定 `POST /api/citations/lookup`。接口接收 DOI，返回查询状态、论文书目信息、NLM 引用文本、缺失关键字段提示和来源信息。
- **处理顺序：**校验并规范化纯 DOI/DOI 链接 → 查询 PubMed → 若 PubMed 未找到记录或关键元数据不足，再查询 Crossref → 只在备用来源返回的 DOI 与输入 DOI 一致时采用其记录 → 规范化元数据并检查支持类型/必填字段 → 生成 NLM 引用 → 返回前端。
- **来源优先级：**PubMed 是首选来源，Crossref 是备用来源。若两个来源的非空字段发生冲突，不静默拼接或覆盖；首版以 PubMed 的值为主。具体冲突提示方式可在实现验收时再细化。
- **业务边界：**仅处理英文医学期刊论文；其他类型不生成期刊引用。查不到记录时不显示空白手动表单或伪造引用；清楚提示用户检查 DOI 或稍后重试。作者、标题、期刊名、年份为空时提醒，但不宣称核实了信息真实性。
- **前端编辑：**接口返回原始查询结果；用户编辑后的字段及引用预览由页面暂存，刷新后不保留。编辑时温和提醒用户对照原文检查；系统不验证用户修改是否真实。
- **首版不设数据库和账号：**查询和编辑不保存到服务端，也不提供跨设备书目、项目或协作。以后确认需要保存书目时再评估数据库与登录。
- **错误情况：**区分 DOI 格式无效、没有匹配记录、资料类型不支持、上游查询失败/超时，以及关键字段缺失；向用户提供清楚的下一步提示。查询接口应设置合理超时并只请求固定可信来源。
- **引用格式工具和速度：**NLM《Citing Medicine》仍是格式基准。具体格式引擎、真实样例核对方式及约 5 秒的暂定速度目标留待实现后验收；如果结果准确度或速度不达标，再调整方案。
- **暂缓决定：**部署平台、缓存、公开服务后的限流策略、自动化测试工具，以及未来账号/项目所需的数据模型均未定；不在首版提前引入。

### 部署方案（2026-10-26 已确认）

- 使用 Cloudflare Workers 运行带有 Next.js Route Handler 的全栈应用。
- 使用 Cloudflare 官方推荐的 vinext 适配现有 Next.js 16 项目；保留原有 `next dev`、`next build` 和 App Router 结构。
- 首版不启用 Cloudflare CDN 缓存、KV/数据库或图片优化；先保证页面和 DOI 查询接口一起可用。
- Cloudflare 上已有的 Pages 项目不能直接当作当前应用版本；静态上传不包含本项目的服务端 DOI 查询接口。
- 最终公开部署前，必须先通过本地 vinext 构建、页面加载和 `POST /api/citations/lookup` 验证。

## 七、风险与待确认事项

- **元数据覆盖和完整度：**DOI 可解析不代表一个来源一定能提供所有论文信息；需要用实际医学文章样本检查。
- **引用准确性：**格式规则和元数据质量是核心风险；必须区分“字段缺失提醒”和“信息真假核验”。
- **外部服务故障和速度：**查询可能变慢、限流或暂时不可用；页面要提供等待、失败和重试反馈。
- **产品切入点：**目标用户是否觉得“更简单、更快”仍需真实使用验证。
- **尚未确定：**部署平台、正式产品名称、引用格式引擎及验证样例、缓存和测试工具、公开服务后的限流策略、未来账号/数据库方案、上线方式。

## 八、产品文案草案

- 工作名称：MedCite，正式使用前需确认名称可用性。
- 首屏标题：**Simple medical citations**
- 副标题：`Paste a DOI to create an NLM-style reference for a medical journal article.`
- 主要操作：输入 DOI，点击“生成引用”，检查并复制结果。

产品表达应突出简单和快速，但不可暗示系统保证元数据完全正确或覆盖所有医学期刊的特殊要求。
